# 注册确认与发送准备修复（2.10.62 / 110）

用户反馈网页注册后打开邮箱链接，仍无法登录。截图实际错误为邮箱未验证。对用户指定账号的只读聚合检查发现：账号存在，2026-10-01 22:02（北京时间）创建，22:05 发出确认邮件，尚未确认、没有成功登录记录。没有修改账号、密码或确认状态；此文不保存邮箱或确认链接。

Supabase 管理面 Site URL 是 https://www.dengtahome.com/，回跳允许列表包含两个正式域名，邮件使用默认模板。13:55–14:45 UTC 的认证网关日志没有 /auth/v1/verify 请求。已确认断点在完成邮箱验证之前，无法仅由这些证据断言 QQ、微信、网络或邮件扫描器是根因。供应商上存在技术问题公告，但不能据此认定本次故障由公告所述事件造成。

前端另有可复现问题：安装的 auth-js 的 getSession() 会等待 initializePromise，但不会返回邮箱回跳初始化的错误。现显式读取 initialize() 结果，将 otp_expired、email_not_confirmed 和其他认证错误显示为原因和稳定代码。初始化错误只读取一次，使用户能够继续密码登录或重新发送邮件；已经有效的设备会话不因重新打开失效链接被隐藏。

登录页新增重新发送入口，只校验邮箱，不强迫用户先填写密码。确认页增加折叠备用验证表单：用户复制最新邮件 Confirm email address 的原始链接，由现有 auth-js 的 verifyOtp 发送 POST 到当前项目认证服务。只接受当前认证项目的 /auth/v1/verify，type=email 或 signup，token/token_hash 必须非空且格式有效；拒绝其他域名、带用户凭据的 URL、密码重置等链接。不使用链接中的 redirect_to，不访问任意目标，不记录或持久化原始链接，输入隐藏且提交后清空。账号仍由 Supabase 正式核验有效凭据；没有管理员确认、绕过验证或关闭认证。

官方协议参考：https://supabase.com/docs/guides/auth/auth-email-templates 。ConfirmationURL 的 token 是 TokenHash，verifyOtp 可直接验证。邮件预取、跟踪改写是官方列出的可能因素，本次未取证确认。默认邮件配置的外部用户适用性和真实邮箱跳转仍需真实用户验收。

此前发送准备流程等设置和模型保存结束后才创建 AbortController，等待期间停止按钮无法取消。现在提前注册请求与信号，每个准备等待都可取消，核对会话身份后才发送；停止后保留普通输入及附件，不在保存晚完成时继续发消息，临时截图按原机制释放。设置未保存给出 chat_preparation_settings_unsaved；准备异常给出 chat_preparation_failed。不会跳过设置保存，也没有新增流式打字缓冲。
